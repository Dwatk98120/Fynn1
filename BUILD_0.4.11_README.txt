HEARLIUM BRANCH 2 — BUILD 0.4.11 — DUPLICATE WAV WRITE BARRIER

Why: The installed Build 0.4.10 created a fourth identical WAV when the user
clicked Recording History > Reanalyze. The four WAVs shared the same recording
ID, speaker ID, size (96,684 bytes) and SHA-256. Their small JSON metadata
records had new session/observation IDs, demonstrating repeated storage entries.

Changes:
- Server-side write barrier blocks creation of another permanent original WAV
  when an existing recording ID already exists and the request does not carry
  the explicit reanalysis intent. Different speaker or audio hash fails closed.
- Existing Android retries with matching recording/session/speaker/name/audio
  retain the previously tested idempotent path.
- Explicit reanalysis still verifies original audio and creates only a separate
  versioned analysis export, without changing original WAV or metadata.
- Windows installer version and visible UI marker are both 0.4.11.
- Added regression tests for missing reanalysis flag, identity conflict, and
  distinct recording IDs with identical audio.

Verification on this Linux source environment:
  python -m pytest -q server/tests
  319 passed, 3 skipped, 41 subtests passed

IMPORTANT: These tests DO NOT prove that the installed Windows UI sends the
correct reanalysis flag. If it does not, the new server guard should block
new WAV creation, but analysis may show a storage error. That is safer than
silently creating more originals. Report any error; do not retry repeatedly.

Windows installer compilation and real Windows reanalysis are NOT tested here.
Run BUILD_HEARLIUM_INSTALLER.bat on Windows, verify build 0.4.11 in the UI,
then inspect the number and hashes of matching WAVs before and after ONE
reanalysis. Preserve all historical WAVs, JSON files and approvals.

Main remains frozen. Branch 2 only. Android client unchanged.
